# سند مبنای محصول PSK Meeting Enterprise

## ۱. هدف
سامانه یکپارچه مدیریت فضاها و اتاق‌های جلسات پاک سیمین کویر برای استفاده کارکنان، مدیران واحدها، مسئولان اتاق و مدیران کل سامانه در تهران و کاشان.

## ۲. داده‌های سازمانی مبنا
- محل‌ها و اتاق‌های شناخته‌شده: تهران `PSK-THR-101`، `PSK-THR-102`، `PSK-THR-103`؛ کاشان `PSK-KSH-201` و `PSK-KSH-202`.
- حدود ۴۲۰ رکورد کاربری گزارش‌شده؛ فعال یا واقعی بودن تک‌تک رکوردها هنوز تأیید نشده است.
- نقش‌های پایه: `SUPER_ADMIN`، `ROOM_ADMIN`، `DEPT_MANAGER`، `EMPLOYEE`.
- امکانات مورد انتظار: رزرو و تأیید، QR، پذیرایی، نظافت، تعمیرات، پیامک، گزارش‌ها و ورود Excel.

## ۳. اصول طراحی برگرفته از بازار جهانی
1. سلسله‌مراتب محل: سازمان ← سایت/شهر ← ساختمان/طبقه (در صورت نیاز) ← اتاق.
2. جلوگیری از رزرو هم‌پوشان در سطح دیتابیس، نه فقط رابط کاربری.
3. جداسازی دسترسی بر اساس نقش و سایت؛ همه APIها باید کنترل مجوز سمت سرور داشته باشند.
4. تحلیل رزرو برنامه‌ریزی‌شده در برابر حضور واقعی؛ در فاز نخست check-in با QR و ثبت دستی، سپس امکان اتصال حسگر.
5. مدیریت امکانات و ظرفیت هر اتاق به‌صورت داده قابل پیکربندی.
6. ثبت رویدادهای حساس و گزارش‌پذیری تغییرات.
7. API مشترک برای وب، PWA، Android و iOS.

## ۴. معماری منتخب
- Monorepo با pnpm workspaces.
- Web/PWA: React + TypeScript + Vite.
- Mobile: React Native + Expo Router.
- API: Node.js + TypeScript + Fastify.
- Database: PostgreSQL 16؛ Prisma برای مدل داده و migrationهای SQL تکمیلی برای قیود دیتابیس.
- استقرار: Docker، reverse proxy با TLS، پشتیبان‌گیری زمان‌بندی‌شده و پایش سلامت.

## ۵. فازبندی تحویل
- فاز صفر: نیازمندی، مدل تهدید، معماری و داده مرجع.
- فاز یک: هویت و دسترسی، سایت‌ها، اتاق‌ها، رزرو و جلوگیری از تداخل.
- فاز دو: تأیید، لغو، QR check-in، اعلان‌ها و پیامک.
- فاز سه: پذیرایی، نظافت، تعمیرات و گردش‌کار خدمات.
- فاز چهار: گزارش‌های مدیریتی، تحلیل استفاده، Excel import با preview و گزارش خطا.
- فاز پنج: سخت‌سازی، آزمون بار، بازیابی پشتیبان، استقرار و خروجی فروشگاهی موبایل.

## ۶. معیارهای پذیرش کلیدی
- رزروهای فعال یک اتاق در بازه‌های هم‌پوشان حتی در درخواست‌های هم‌زمان نباید ثبت شوند.
- کاربر غیرمجاز نباید داده سایت دیگر را از هیچ endpoint دریافت کند.
- تغییر نقش، غیرفعال‌سازی یا تغییر سایت کاربر باید نشست‌های قبلی او را بی‌اعتبار کند.
- هیچ پیامک واقعی در محیط توسعه/تست ارسال نشود.
- ورود گروهی کارکنان فقط پس از تأیید فایل، پیش‌نمایش تغییرات و تأیید مجاز انجام شود.
- گزارش‌ها باید با داده‌های واقعی و تعریف روشن شاخص‌ها ساخته شوند؛ داده نمایشی با داده عملیاتی مخلوط نشود.

## ۷. وضعیت نسخه توسعه‌یافته 0.2

در مخزن فعلی، اسکلت اولیه به نسخه توسعه‌یافته 0.2 ارتقا یافته است:
- وب‌سایت معرفی مستقل در `apps/website` و وب‌اپ/PWA در `apps/web`.
- اپلیکیشن Android/iOS در `apps/mobile` با SecureStore، تولید QR و اسکن QR.
- API احراز هویت، نشست، قفل ورود، تغییر رمز و بازیابی OTP پیامکی.
- مدیریت سایت/اتاق، رزرو، تصمیم‌گیری، لغو و تکمیل با کنترل هم‌زمانی دیتابیس.
- خدمات پذیرایی، نظافت و تعمیرات؛ گزارش استفاده و CSV.
- Excel Preview/Commit تراکنشی با کنترل شعب و تکراری‌ها.
- Docker Compose، Health/Readiness، Nginx، PWA، seed داده مرجع و اسکریپت‌های Backup/Restore.

## ۸. مواردی که هنوز اثبات یا تکمیل نشده‌اند

این نسخه هنوز Production Ready اعلام نمی‌شود. در محیط ساخت حاضر دسترسی شبکه برای دریافت پکیج‌ها و Docker/Compose وجود نداشت؛ بنابراین موارد زیر اجرا نشده‌اند:
- `pnpm install`، Prisma generate/validate/migrate واقعی و typecheck کامل با وابستگی‌ها.
- Build واقعی وب‌سایت، وب‌اپ و API؛ اجرای PostgreSQL و آزمون end-to-end.
- تست بار ۴۰۰ کاربر، تست امنیت مستقل و آزمون بازیابی روی سرور هدف.
- ساخت APK/AAB/IPA امضاشده و انتشار در فروشگاه‌ها.
- اتصال عملیاتی Kavenegar، آزمون OTP با سرویس واقعی و ارسال پیامک.
- ورود اطلاعات واقعی کارکنان؛ هیچ رکورد کارمند واقعی در Seed ایجاد نشده است.

فایل `docs/GO_LIVE_CHECKLIST_FA.md` معیار پذیرش قبل از راه‌اندازی رسمی است. تا تکمیل آن، وضعیت نسخه Stage/Pilot است.
